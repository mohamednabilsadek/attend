# Hudoori | نظام الحضور الجامعي
**Bilingual University Attendance Management System**  
منصة ويب لتسجيل ومتابعة حضور وانصراف الطلاب في المقررات والمحاضرات، مع واجهة عربية وإنجليزية ودعم الأجهزة المحمولة.

> **حالة هذا المستند:** دليل تشغيل ونشر مُنظَّم اعتمادًا على المعلومات المتاحة في الملف الأصلي. لم تتم مراجعة ملفات التطبيق البرمجية نفسها؛ لذلك لا يُفترض أن جميع الخصائص المذكورة هنا قد خضعت لمراجعة أمنية مستقلة.

## 1. نظرة عامة | Overview

**Hudoori** هو مشروع ويب لإدارة تسجيل حضور الطلاب ومتابعة سجلات الحضور للمقررات والمحاضرات. يوضح ملف المشروع مسارين للنشر:

1. **استضافة بسيطة:** واجهة على GitHub Pages مع واجهة خلفية باستخدام Google Apps Script، وتخزين البيانات في Google Drive.
2. **استضافة ذاتية:** خادم Node.js على Ubuntu يقدم الواجهة وواجهة API ويخزن البيانات محليًا على الخادم.

### أهداف المشروع

- واجهة قابلة للاستخدام من المتصفح على الكمبيوتر والهاتف.
- دعم اللغتين العربية والإنجليزية.
- إدارة حسابات المستخدمين وفق الأدوار المتاحة في التطبيق.
- تسجيل ومراجعة سجلات الحضور.
- دعم النسخ الاحتياطي والاستعادة وفق طريقة الاستضافة.

> **مهم:** يجب التحقق من تفاصيل الأدوار والصلاحيات وآلية تسجيل الحضور من ملفات التطبيق الفعلية قبل اعتماد النظام للاستخدام الرسمي.

## 2. طرق التشغيل | Deployment Options

| الخيار | مناسب لـ | المزايا | اعتبارات |
|---|---|---|---|
| GitHub Pages + Google Apps Script | تجربة أولية أو مجموعة صغيرة | إعداد بسيط ولا يتطلب إدارة خادم Ubuntu | يعتمد على حصص Google Apps Script وحدود التنفيذ المتزامن |
| Ubuntu + Node.js + HTTPS | كلية أو قسم أو تشغيل داخلي أوسع | تحكم أكبر في الاستضافة والبيانات وإعدادات الخادم | يتطلب إدارة الخادم والتحديثات والحماية والنسخ الاحتياطي |

**اقتراح عملي:** اختبر النظام أولًا على نطاق محدود، ثم نفّذ تجربة ضغط واقعية قبل استخدامه في محاضرات كبيرة أو اعتماد سجلاته رسميًا.

## 3. المتطلبات | Requirements

### خيار Google Apps Script

- حساب Google وصلاحية استخدام Google Drive.
- مشروع Google Apps Script.
- مستودع GitHub يحتوي على ملفات الواجهة.
- رابط نشر Web App ينتهي بـ `/exec`.
- اتصال HTTPS حتى تعمل أذونات الكاميرا والموقع في المتصفحات المدعومة.

### خيار Ubuntu

- خادم Ubuntu.
- Node.js إصدار 16 أو أحدث وفق الدليل الأصلي؛ يُفضَّل اعتماد إصدار مدعوم أمنيًا وقت التثبيت.
- ملفات حزمة `hudoori-selfhost`.
- صلاحيات إدارية للتثبيت وإعداد خدمة systemd.
- Caddy أو حل HTTPS مكافئ.
- مساحة تخزين كافية للبيانات والنسخ الاحتياطية.

## 4. النشر باستخدام GitHub Pages وGoogle Apps Script

### الخطوة 1: إنشاء مشروع Apps Script

1. افتح [Google Apps Script](https://script.google.com).
2. أنشئ مشروعًا جديدًا.
3. انسخ محتويات `Code.gs` إلى المشروع.
4. غيّر قيمة `SETUP_CODE` من القيمة الافتراضية إلى رمز سري قوي وفريد.
5. احفظ المشروع.

### الخطوة 2: منح الصلاحيات ونشر Web App

1. شغّل الدالة `authorize` وامنح الصلاحيات المطلوبة بعد مراجعتها.
2. اختر **Deploy → New deployment → Web app**.
3. وفق الإعدادات الواردة في الدليل الأصلي:
   - **Execute as:** Me
   - **Who has access:** Anyone
4. انشر التطبيق واحتفظ بعنوان URL الذي ينتهي بـ `/exec`.

> **تحذير أمني:** إعداد الوصول إلى **Anyone** قد يجعل نقطة API متاحة للجمهور. لا تعتمد هذا الإعداد في بيئة جامعية فعلية قبل مراجعة المصادقة والتحقق من الصلاحيات ومقاومة إساءة الاستخدام، والتأكد من أن البيانات لا يمكن قراءتها أو تعديلها دون تفويض مناسب.

### الخطوة 3: ربط الواجهة بواجهة API

1. افتح `pages/config.json`.
2. استبدل `PASTE_WEB_APP_URL_HERE/exec` بعنوان Web App الصحيح.
3. تحقق من صحة JSON ومن عدم وجود مسافات أو أحرف زائدة في الرابط.

يمكن للدليل الأصلي أيضًا فتح الصفحة باستخدام معامل URL بالشكل التالي:

```text
index.html?api=<exec_url>
```

### الخطوة 4: النشر على GitHub Pages

1. ارفع ملفات الواجهة المطلوبة، ومنها `index.html` و`config.json`، إلى المستودع.
2. افتح **Settings → Pages**.
3. اختر الفرع `main` والمجلد `/root` إذا كانت هذه هي بنية المستودع.
4. انتظر اكتمال النشر ثم افتح رابط الموقع عبر HTTPS.
5. اختبر إنشاء قاعدة البيانات وتسجيل الدخول وإضافة المحاضرين وتسجيل الطلاب من حسابات اختبار.

### الخطوة 5: الإعداد الأولي

1. افتح الموقع.
2. انتقل إلى **Admin → Create Database**.
3. أدخل بيانات الإعداد ورمز `SETUP_CODE`.
4. أضف حسابات المحاضرين وفق واجهة الإدارة.
5. اختبر تسجيل حساب طالب جديد والتحقق من الصلاحيات.

### تحديث Apps Script

عند تعديل `Code.gs`:

1. افتح **Deploy → Manage deployments**.
2. اختر النشر الحالي ثم **Edit**.
3. أنشئ إصدارًا جديدًا.
4. اختبر واجهة API بعد التحديث.

## 5. الاستضافة على Ubuntu

بحسب الدليل الأصلي، تستخدم الحزمة خادم Node.js واحدًا لتقديم الواجهة وواجهة API. ويُذكر أن البيانات تحفظ في:

```text
/opt/hudoori/data/hudoori-db.json
```

وتُحفظ النسخ اليومية في مجلد `data/backups/` مع الاحتفاظ بآخر 30 نسخة. تحقّق من هذه المسارات في الحزمة الفعلية قبل تنفيذ أي إجراء.

### الخطوة 1: نسخ الملفات وتثبيت الخدمة

انسخ مجلد الحزمة إلى الخادم ثم نفّذ الأوامر التالية بعد التأكد من المسارات ومصدر الملفات:

```bash
scp -r hudoori-selfhost user@SERVER:~/
ssh user@SERVER
cd hudoori-selfhost
sudo bash install.sh
```

### الخطوة 2: ضبط رمز الإعداد

افتح ملف البيئة:

```bash
sudo nano /opt/hudoori/hudoori.env
```

غيّر `SETUP_CODE` إلى قيمة سرية قوية وفريدة. لا تستخدم القيمة الافتراضية، ولا تضع الرمز في مستودع GitHub أو في ملفات عامة.

### الخطوة 3: تشغيل الخدمة والتحقق منها

```bash
sudo systemctl enable --now hudoori
systemctl status hudoori
```

يمكن إجراء اختبار محلي مبدئي وفق الدليل الأصلي:

```bash
curl -s localhost:8080/api -d '{"op":"status"}'
```

إذا لم تعمل الخدمة، راجع السجلات:

```bash
journalctl -u hudoori -f
```

### الخطوة 4: إعداد HTTPS باستخدام Caddy

يحتاج الوصول إلى الكاميرا والموقع الجغرافي في المتصفح عادةً إلى HTTPS، باستثناء سياقات موثوقة مثل `localhost`.

**شبكة داخلية فقط:** يمكن إعداد اسم داخلي مثل `hudoori.lan` مع شهادة محلية. ستحتاج الأجهزة إلى الوثوق بجهة إصدار الشهادة وفق إعدادات Caddy؛ وإلا فقد تظهر تحذيرات أو تفشل بعض الأذونات.

**نطاق عام:** يمكن استخدام نطاق تملكه مع Caddy وLet's Encrypt، بعد ضبط DNS والسماح بالوصول المطلوب إلى المنفذين 80 و443.

**دون فتح منافذ مباشرة:** يمكن دراسة Cloudflare Tunnel أو Tailscale بحسب سياسة الشبكة ومتطلبات الخصوصية.

> أبقِ المنفذ `8080` غير متاح من الإنترنت. يذكر الدليل أن التطبيق يستمع على `127.0.0.1` وأن Caddy يستقبل اتصالات HTTPS. تحقّق من ذلك فعليًا باستخدام إعدادات الخادم والجدار الناري.

### الخطوة 5: أول تشغيل

1. افتح عنوان الموقع عبر HTTPS.
2. انتقل إلى **Admin → Create Database**.
3. أدخل رمز الإعداد الذي ضبطته في ملف البيئة.
4. أنشئ حسابات اختبار واختبر الوظائف الأساسية قبل إدخال بيانات حقيقية.

### تحديث التطبيق

بعد مراجعة التغييرات وأخذ نسخة احتياطية:

1. حدّث الملفات وفق آلية الإصدار المعتمدة.
2. لا تستبدل مجلد البيانات.
3. أعد تشغيل الخدمة:

```bash
sudo systemctl restart hudoori
```

4. تحقق من حالة الخدمة وسجلاتها، ثم اختبر تسجيل الدخول والحضور والنسخ الاحتياطي.

## 6. النسخ الاحتياطي واستعادة البيانات

### الاستضافة باستخدام Google Apps Script

- استخدم وظيفة **Export Encrypted Backup** من الإعدادات عند توفرها.
- احتفظ بالنسخة في موقع خاص وآمن خارج المستودع العام.
- اختبر الاستعادة دوريًا باستخدام نسخة اختبار، لا على قاعدة البيانات الإنتاجية مباشرة.

### الاستضافة الذاتية على Ubuntu

- يذكر الدليل أن هناك نسخًا يومية تحتفظ بآخر 30 نسخة؛ تحقق من نجاح النسخ ومن إمكانية استعادتها.
- انسخ البيانات دوريًا إلى موقع منفصل عن الخادم.
- قيّد صلاحيات قراءة ملفات البيانات والنسخ الاحتياطية.
- لاحظ أن ملف قاعدة البيانات المحلي موصوف في الدليل بأنه **غير مشفر**؛ لذلك يجب حمايته بتصاريح النظام والتشفير المناسب للتخزين والنسخ الخارجية.

### الانتقال من Google إلى Ubuntu

وفق الدليل الأصلي:

1. صدّر نسخة احتياطية مشفرة من إعدادات الإصدار القديم.
2. افتح إصدار Ubuntu.
3. اختر **Admin → Restore Backup**.
4. اتبع خطوات الاستعادة باستخدام رمز الإعداد الجديد.
5. تحقق من عدد المستخدمين والمقررات وسجلات الحضور بعد الاستعادة.

لا تعتبر عملية الترحيل مكتملة حتى تتأكد من سلامة البيانات وتطابقها.

## 7. الأداء والسعة المتوقعة

الأرقام التالية من قياسات تجريبية مذكورة في الملف الأصلي، وليست ضمانًا للأداء في بيئة إنتاجية. تختلف النتائج حسب مواصفات الخادم والشبكة والأجهزة وطبيعة الطلبات.

| السيناريو المذكور في الدليل | حجم قاعدة البيانات | النتيجة المذكورة |
|---|---:|---|
| 500 طالب و30 مقررًا، نحو 30,000 سجل | 8 MB | نحو 950 طلبًا/ثانية، وأبطأ 5% قرابة 0.28 ثانية |
| 3,000 طالب و100 مقرر، نحو 214,000 سجل | 56 MB | نحو 640 طلبًا/ثانية، وأبطأ 5% قرابة 0.6 ثانية |

يشير الدليل إلى أن هذه القياسات تمت على خادم محلي تجريبي، وأن لوحة الإدارة التي تحمّل جميع سجلات الحضور دفعة واحدة قد تصبح بطيئة مع قواعد البيانات الكبيرة.

### توصيات قبل التوسع

- أجرِ اختبار ضغط على الخادم والشبكة الفعليين.
- اختبر سيناريو المسح المتزامن لرمز QR من عشرات الأجهزة.
- أضف ترقيم الصفحات أو التحميل التدريجي للسجلات إذا كان عددها كبيرًا.
- راقب زمن الاستجابة واستهلاك الذاكرة ومساحة القرص وأخطاء API.
- اختبر الطلبات المرفوضة، ومحاولات تسجيل الدخول المتكررة، وانقطاع الشبكة.

## 8. ملاحظات أمنية مهمة

هذا القسم قائمة تحقق أولية، وليس تأكيدًا بأن التطبيق يطبق جميع الضوابط:

- **المصادقة والصلاحيات:** تحقق من أن كل عملية إدارية أو أكاديمية تتحقق من هوية المستخدم وصلاحياته على الخادم، وليس في الواجهة فقط.
- **حماية البيانات:** لا تضع قواعد البيانات أو النسخ الاحتياطية أو الأسرار في مستودع عام.
- **رمز الإعداد:** استخدم رمزًا قويًا وفريدًا، وغيّره إذا انكشف. لا تعتمد على سر ثابت داخل ملفات الواجهة.
- **كلمات المرور:** راجع آلية تخزين كلمات المرور وإعادة تعيينها. يذكر الدليل الأصلي أن كلمات المرور مرتبطة بالبريد الإلكتروني؛ ينبغي تدقيق هذا التصميم قبل الاستخدام الفعلي، وعدم الاعتماد على البريد وحده كوسيلة آمنة لاشتقاق كلمات المرور.
- **الخصوصية:** اجمع أقل قدر لازم من بيانات الطلاب، وحدد من يمكنه الاطلاع على سجلات الحضور ومدة الاحتفاظ بها.
- **الموقع والكاميرا:** وضّح للمستخدم سبب طلب الأذونات وكيفية استخدام البيانات، واختبر سلوك النظام عند رفض الإذن.
- **سجل التدقيق:** يُنصح بتسجيل العمليات الإدارية المهمة والتعديلات على سجلات الحضور مع هوية المنفذ والتوقيت.
- **التحديثات:** حدّث نظام التشغيل وNode.js والاعتماديات، وراجع إعدادات HTTPS والجدار الناري دوريًا.
- **النسخ الاحتياطي:** اختبر الاستعادة فعليًا، ولا تكتفِ بوجود ملفات النسخ.
- **الاعتماد الرسمي:** نفّذ مراجعة أمنية واختبار صلاحيات وخصوصية قبل استخدام النظام في سجلات جامعية رسمية.

## 9. استكشاف الأخطاء وإصلاحها

| المشكلة | ما يجب فحصه |
|---|---|
| الكاميرا أو الموقع لا يعملان | افتح الموقع عبر HTTPS، وافحص أذونات المتصفح وسياسة الجهاز |
| الواجهة لا تتصل بواجهة API | راجع رابط `/exec` في `config.json`، وصحة النشر، وأخطاء الشبكة في أدوات المطور |
| الخدمة لا تعمل على Ubuntu | استخدم `systemctl status hudoori` ثم `journalctl -u hudoori -f` |
| لا تظهر البيانات بعد إعادة التشغيل | تحقق من مسار البيانات وصلاحيات الملفات وسجلات الخدمة والنسخ الاحتياطية |
| تظهر أخطاء بعد تحديث Apps Script | تأكد من نشر إصدار جديد، ومن صحة رابط Web App، ثم اختبر العمليات الأساسية |
| النظام بطيء مع سجلات كثيرة | افحص حجم الاستجابة، وأداء الخادم، وإمكانية إضافة ترقيم الصفحات أو التحميل التدريجي |
| تظهر تحذيرات شهادة HTTPS داخل الشبكة | تحقق من اسم النطاق والشهادة ومن إعداد الثقة على الجهاز |

## 10. قائمة التحقق قبل الإطلاق

- [ ] اختبار الواجهة العربية والإنجليزية واتجاه RTL/LTR.
- [ ] اختبار التصميم على هاتف صغير وجهاز لوحي وكمبيوتر.
- [ ] اختبار أدوار المسؤول والمحاضر والطالب، كلٌّ بحساب مستقل.
- [ ] التأكد من عدم قدرة الطالب على تعديل سجلات أو بيانات ليست من صلاحياته.
- [ ] اختبار إنشاء المقررات والفرق والمحاضرات وفق وظائف التطبيق الفعلية.
- [ ] اختبار تسجيل الحضور ومنع التسجيل المكرر إذا كان ذلك مطلوبًا.
- [ ] اختبار الكاميرا والموقع بعد منح الأذونات وبعد رفضها.
- [ ] اختبار النسخ الاحتياطي والاستعادة على بيئة تجريبية.
- [ ] التأكد من عدم وجود أسرار أو بيانات طلاب في مستودع عام.
- [ ] إجراء اختبار ضغط واقعي ومراجعة السجلات والأخطاء.
- [ ] توثيق مسؤول النظام وآلية الدعم والتحديث والاستعادة.
- [ ] الحصول على الموافقات الجامعية اللازمة قبل تشغيل النظام ببيانات حقيقية.
